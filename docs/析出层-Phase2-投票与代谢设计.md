# 析出层 Phase 2：投票、分类与代谢（设计稿，已实现于 v0.23.0，见 README.md）

Phase 1（LLM 抽取 + 存储 + 展示，含"查看原文"永久快照）已经完成并上线。这份文档是 Phase 2 的设计——投票、分类、生命周期/代谢——实现前先落盘,供实现时对照。**当前实际行为以 [README.md](../README.md) 的"析出层（Phase 1 + Phase 2）"一节为准**,这份文档保留作为"当初为什么这么设计"的历史记录,不再随实现变化更新。

对应 [构想摘要.md](构想摘要.md) 里"结晶/结石/矿渣/化石"四分类的原始设想。这份设计**简化成了二元判断（Good / 不是 Good）**，原因见下文"为什么不是四分类"。

---

## 1. 为什么不是四分类

原设想的四分类把"质量判断"和"生命周期/保留策略"揉在一起设计，很有叙事层次，但依赖有意义的投票量才能撑得起来。这个产品现在（以及可预见的一段时间内）单个帖子的投票参与度大概率很低——大多数人不会主动投票，"没表态"会是绝对多数。在这个前提下：

* 四路分票会把本来就稀薄的信号切得更碎，容易被噪音主导；
* 门槛设高了（比如要求最少票数才能定档），大部分帖子可能永远够不着任何一档，机制形同虚设，等于白做；
* 门槛设低了，跟简化成二元判断比起来又没有实质区别，只是多了复杂度。

所以先做最简单、最可能真正跑起来的版本：**Good / 不是 Good** 两态，配合下面的动态重算机制保留原设想里"分类会随投票翻转"的核心精神。等真实投票数据积累出来，如果发现二元判断确实丢了重要信息，再考虑往回加层次——不在这个阶段赌四分类一定能跑起来。

---

## 2. 数据模型

新增一张表，跟 `posts` 表同库（每个房间自己的 `ChatRoom` Durable Object）：

```sql
CREATE TABLE IF NOT EXISTS post_votes (
  post_id TEXT NOT NULL,
  hash_id TEXT NOT NULL,
  vote TEXT NOT NULL CHECK (vote IN ('good', 'bad')),
  updated_ts INTEGER NOT NULL,
  PRIMARY KEY (post_id, hash_id)
)
```

* 一个人对一个帖子只有一行（`PRIMARY KEY (post_id, hash_id)`），改票就是 `INSERT ... ON CONFLICT (post_id, hash_id) DO UPDATE`，天然支持"改主意"。
* `hash_id` 复用聊天室现成的匿名身份体系（跟发言用的是同一套 secret → hash 机制），投票身份 = 这个人在本房间的聊天身份，不是另起一套。
* **不单独存"当前分类"字段**。净分数（好票数 − 坏票数）每次要用的时候（渲染帖子页、GC 扫描）现查现算，不缓存——帖子量级小，SQL 现算比维护一个可能跟真实票数脱节的缓存字段更省心，也不会有"缓存没更新"这类 bug。

`posts` 表本身不需要改动（`created_ts` 已经有了，观察期判断直接用它）。

---

## 3. 分类规则

单一判断，不设"中立"档：

> **净分数（好票 − 坏票）> 0 → Good；否则（含 0 票、平票、净负）→ 不是 Good。**

"不是 Good"不是一个需要主动投出来的负面判定，是默认状态本身——这样"长期没人理睬的帖子"和"被明确投差评的帖子"落在同一侧，都会被下面的 GC 清理掉，不会无限堆积占版面。

---

## 4. 新帖观察期

`posts.created_ts` 距今不满一个完整 GC 周期（见第 5 节，当前是 7 天）的帖子，GC 扫描时直接跳过，不参与本次判定。

保证每个帖子至少有一整个周期被人看到、投票的机会，不会因为析出时机刚好卡在 GC 边界附近就被误杀——这跟"长期没人理会"是两回事，不该用同一把尺子。

---

## 5. GC 周期与执行

**周期**：固定一周一次，`wrangler.jsonc` 加 Cron Trigger：

```jsonc
"triggers": { "crons": ["0 0 * * SUN"] }  // 每周日 00:00 UTC(Cloudflare 不接受数字 0 代表周日,实测踩过一次)
```

**执行方式**：中心 cron 只做分发，不做重活；真正的清算逻辑分散在各房间自己的 DO 里跑，避免重蹈 `RoomRegistry` 曾经当过全站唯一瓶颈的覆辙。

```
scheduled() [index.ts]
  → RoomRegistry.listRoomsForGc(now)   // 新增 RPC，读 known_rooms 表（已存在，不用新建），
                                        // 用 created_ts 过滤掉创建不满一个周期的房间
  → 对每个房间名：
      ChatRoom(room).runWeeklyGc()    // 新增 RPC，各房间自己算、自己删
```

所有房间统一同一个 GC 时间点（不按各自创建时间错峰）——房间量级现在小，统一时间点实现简单；量级真的大到"全站房间同一秒扇出"变成问题时，再考虑错峰或者 Cloudflare Queues 异步扇出，现在不用为这个还没出现的规模先做复杂设计。中心循环用顺序或小批量并发调用即可。

**`runWeeklyGc()` 内部逻辑**（跑在每个房间自己的 DO 里）：

```
for post in posts WHERE now - created_ts >= GC_CYCLE_MS:
    netScore = SUM(CASE WHEN vote='good' THEN 1 ELSE -1 END) FROM post_votes WHERE post_id = post.id
    if netScore <= 0:
        DELETE FROM posts WHERE id = post.id
        DELETE FROM post_votes WHERE post_id = post.id
```

硬删，不留痕迹，跟现有的消息滚动删除、没有软删除机制的风格一致。

## 6. 投票怎么提交

帖子页（`/posts`）目前是纯服务端渲染、零 JS 交互的页面，投票需要加一点客户端逻辑：

* 复用聊天页那套 localStorage 里的 `secret`（同一个 key，同源共享），没有就跟聊天页一样随机生成一个。
* 每个帖子卡片上直接放 好 / 坏 两个投票按钮，不需要先点开"查看原文"弹窗才能投——减少投票门槛。
* 点击后 `POST /posts/<postId>/vote`，body 带 `{ secret, vote }`；`index.ts` 用 secret 算出 hashId（复用 `computeHashId`），转发给对应房间的 `ChatRoom.castVote(postId, hashId, vote)`。
* 响应直接带回最新的 `{ netScore, myVote }`，前端原地更新按钮高亮和票数显示，不用整页刷新。
* 跟 `/ws` 一样做 Origin 校验，防跨站提交；走现有的通用 HTTP 限流（`isGeneralRateLimited`）就够，不用为投票单独加一层。
* **投票不能撤回成"没投过"，只能在好/坏之间切换**——先不做撤回，这个可以后面按需加，不影响核心机制先跑起来。

## 7. 展示

帖子页每个卡片，根据当前状态显示不同东西：

| 状态 | 显示 |
|---|---|
| 还在观察期 | "新帖子，观察期还剩 N 天"，不显示清理倒计时 |
| 观察期已过 + 当前 Good | "已保留" 确定态标记，没有倒计时 |
| 观察期已过 + 当前不是 Good | 进度条 + "距下次清理还有 N 天（当前 M 好评 / K 差评），投一票帮它留下" |

* 进度条填充比例 = 距上次 GC 过去的时间 / 一个周期长度（7 天）。
* 好/坏票数直接展示原始数字，透明，不藏着。
* 投票按钮高亮显示"你投的是哪个"。
* "观察期已过 + 不是 Good"这一档天然是大多数帖子的默认命运（0 票也落在这一侧），倒计时 + 投票按钮组合起来是拉动投票参与度的钩子，直接回应"投票机制会不会没人用"这个顾虑。

---

## 8. 明确不做（这个阶段）

* 投票撤回（见第 6 节）
* 各房间错峰 GC（见第 5 节）
* 人工审核/管理员覆盖投票结果——延续现有"防滥用全部自动化规则，没有人工介入"的一贯风格
* 删除时的通知/告示——创建帖子有 toast 提示，删除是静默的，不特意再做一套
